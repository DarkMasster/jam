# Инструкции для ИИ-агентов

Этот репозиторий используется командой на 48-часовом геймджеме. Скорость важна,
но рабочая сборка и сохранение командного контекста важнее количества фич.

## Перед началом любой задачи

Прочитай по порядку:

1. `docs/jam/README.md`
2. `docs/jam/DEVELOPMENT_SPEC.md`
3. `docs/jam/GAME.md`
4. `docs/jam/STORY.md`
5. `docs/jam/QUESTIONS.md`
6. `docs/jam/STATE.md`
7. `docs/jam/BACKLOG.md`
8. `docs/jam/CONTRACTS.md`
9. `docs/jam/INTEGRATIONS.md`
10. `docs/jam/GIT.md`
11. `docs/jam/OFFICE_ROADMAP.md`, если задача касается офисного эпизода
12. назначенный файл из `docs/jam/tasks/`

Если задача противоречит этим документам, остановись и явно опиши конфликт.

## Правила выполнения

- Работай только в назначенной feature-ветке и только в области файлов задачи.
- Не расширяй scope без подтверждения продюсера.
- Предпочитай минимальное рабочее решение, которое можно проверить в текущем билде.
- Не меняй общие контракты, сцены, настройки проекта и публичные интерфейсы без
  согласования.
- Не выполняй commit, merge, push или удаление веток без явного поручения человека.
- После работы заполни `Handoff` в файле задачи.
- Если изменились факты о проекте, обнови `STATE.md`; если изменился интерфейс
  между системами — `CONTRACTS.md`; если принято важное решение — `DECISIONS.md`.
- Не форматируй Unity YAML (`.asset`, `.unity`, `.prefab`, `.meta` и родственные
  файлы) внешним formatter и не удаляй в нём пробелы в конце строк: сериализатор
  Unity использует `key: ` для некоторых пустых значений. При шумовом diff сначала
  сравни семантику и сохрани канонический вывод текущей версии Unity.

### Обязательное правило для офисного эпизода

- Любая работа со сценой, кодом, контентом, интеграциями, тестами или документацией
  офиса начинается с полного чтения `docs/jam/OFFICE_ROADMAP.md`.
- Перед `Handoff` исполнитель редактирует roadmap в той же ветке: обновляет
  затронутый milestone, проверенные факты, блокеры и следующий срез, затем добавляет
  строку в историю изменений.
- Офисную задачу нельзя переводить в `Done`, пока roadmap не обновлён.

### Unity MCP: экономия контекста и проверки

- До вызовов Unity составь план и объедини связанные изменения. Для двух и более
  независимых операций используй `batch_execute`; зависимые операции разделяй
  только там, где следующей нужен результат предыдущей.
- Массовые повторяющиеся изменения выполняй одним C# Editor-скриптом с циклами,
  а не серией однотипных MCP-вызовов. Исходный код редактируй файловыми
  инструментами; Unity MCP используй только для действий, которым нужен Editor.
- Не сканируй весь проект, `AssetDatabase`, сцену или иерархию без явной
  необходимости. Используй точные пути ассетов и сцен, hierarchy paths, имена
  объектов, компонентов и тестов. После пакета проверяй только изменённую область.
- Держи активными только нужные группы Unity MCP-инструментов и отключай временные
  группы после работы, если сервер поддерживает управление группами.
- После изменений сначала дождись компиляции. При ошибках не запускай тесты;
  сначала запроси не более пяти релевантных ошибок без stack trace и получай
  полный stack trace только для выбранной неразрешённой ошибки.
- Все автоматические проверки и прогоны выполняй через Unity Test Framework:
  EditMode — для чистой логики, конфигураций и Editor-кода; PlayMode — для сцен,
  компонентов, физики, поведения во времени и взаимодействий.
- Сначала запускай только тесты изменённой подсистемы по имени, группе, категории
  или assembly. Полные EditMode- и PlayMode-наборы запускай после крупного блока
  или перед сборкой, а не после каждого небольшого изменения.
- Запрашивай краткую сводку тестового прогона. Детали и stack trace получай только
  для упавших или пропущенных тестов; после исправления повторяй сначала конкретный
  тест, затем его группу. После успешного прогона не перечитывай Console.
- Не запускай ручной Play Mode, если результат можно проверить PlayMode-тестом.
  Скриншот и ручной прогон оставляй для одной финальной визуальной проверки UI,
  композиции, анимации или эффектов, когда это действительно требуется.
- Для обычной задачи стремись к циклу: точечная инспекция → пакет изменений →
  компиляция → целевые EditMode-тесты → целевые PlayMode-тесты → одна финальная
  визуальная проверка при необходимости. Не возвращай пользователю сырые большие
  ответы Unity MCP, если достаточно краткого результата.

## Формат результата

Укажи:

- что сделано;
- какие файлы изменены;
- как результат проверен;
- что осталось или заблокировано;
- hash последнего коммита, если commit был явно поручен.
