# Правила работы с Git

## Основной принцип

- Основная интеграционная ветка проекта — `main`.
- Напрямую работать и создавать коммиты в `main` запрещено.
- Каждая отдельная задача выполняется в собственной feature-ветке.
- После завершения и проверки задача вливается в `main`.
- После merge feature-ветка не удаляется ни локально, ни в удалённом репозитории.

## Именование веток

Используем понятные имена в нижнем регистре через дефис:

```text
feature/player-dash
feature/enemy-spawn
feature/main-menu
fix/webgl-build
polish/hit-feedback
```

Одна ветка должна соответствовать одной задаче или одному небольшому исправлению.

## Начало работы

1. Убедиться, что в рабочей директории нет чужих незакоммиченных изменений.
2. Получить актуальное состояние `main`.
3. Создать новую ветку от актуального `main`.
4. Отметить задачу как взятую в работу и указать владельца ветки.

Пример:

```bash
git switch main
git pull
git switch -c feature/player-dash
```

Если ветка уже существует, новая ветка с тем же именем не создаётся — участник
продолжает работу в существующей ветке после синхронизации с командой.

## Работа в feature-ветке

- Коммиты должны быть небольшими, рабочими и относиться к задаче ветки.
- Не добавлять в коммит временные файлы, локальные настройки, секреты и случайные
  изменения чужих файлов.
- Перед изменением общей сцены, prefab, настроек проекта или публичного интерфейса
  согласовать это с командой.
- Не переписывать опубликованную историю ветки без согласования с её владельцем.
- Не использовать destructive-команды вроде `git reset --hard` для удаления чужих
  изменений.

Рекомендуемый формат сообщения коммита:

```text
feat: add player dash cooldown
fix: prevent enemy spawn outside arena
polish: add hit feedback
docs: update gameplay contract
```

## Готовность к merge

Ветка готова к слиянию, если:

- выполнены критерии готовности задачи;
- проект запускается и собирается;
- изменённая механика проверена вручную;
- нет известных блокирующих ошибок;
- долговременная память проекта обновлена, если изменились состояние, интерфейсы
  или командные договорённости;
- изменения просмотрены хотя бы одним другим участником, когда это возможно.

## Слияние в main

1. Синхронизировать feature-ветку с актуальным `main`.
2. Разрешить конфликты внутри feature-ветки.
3. Повторно проверить проект.
4. Влить feature-ветку в `main` отдельным merge-коммитом.
5. Отправить обновлённые `main` и feature-ветку в удалённый репозиторий.
6. Feature-ветку не удалять после merge.

Пример локального слияния:

```bash
git switch feature/player-dash
git merge main
# Проверить проект и исправить конфликты, если они появились.

git switch main
git merge --no-ff feature/player-dash
git push origin main
git push origin feature/player-dash
```

Ключ `--no-ff` сохраняет отдельный merge-коммит и делает историю задач заметной.

## Срочные исправления

Даже критическое исправление выполняется в отдельной ветке `fix/<name>`, после
чего проверяется и вливается в `main` по тем же правилам. Исключения допускаются
только по явному общему решению команды.

## Правила для ИИ-агентов

Перед изменениями ИИ-агент обязан:

1. Прочитать этот файл и описание назначенной задачи.
2. Проверить текущую ветку и состояние рабочей директории.
3. Не переключать ветку при наличии незакоммиченных чужих изменений.
4. Не работать напрямую в `main`.
5. Не выполнять merge, push или удаление ветки без явного поручения человека.
6. В итоговом сообщении перечислить изменённые файлы, выполненные проверки и
   известные ограничения.
